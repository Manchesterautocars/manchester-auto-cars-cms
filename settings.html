How Vehicle Images Work

Photos upload directly from the browser to Cloudinary using a short-lived, per-upload signature generated by /api/cloudinary-sign. The CMS only ever stores the resulting Cloudinary web address — never the image data itself, and never in localStorage or GitHub. Images are organised in Cloudinary under manchester-auto-cars/vehicles/<vehicle-id>/.

How Publishing Works

"Publish" sends the full vehicle list to /api/publish-vehicles, which commits data/vehicles.json to on branch . Vercel then rebuilds the public Manchester Auto Cars website from that commit. "Pull Latest" reads the same file back from GitHub so the CMS never has to trust what's cached in this browser.

Security

  • Access to this CMS is controlled by Vercel's deployment protection, not by a page in this app.
  • No GitHub token or Cloudinary API secret exists anywhere in this codebase, in browser storage, or in any API response — only in Vercel environment variables, read server-side by the functions in /api.
  • Cloudinary's API key (not the secret) is returned to the browser by /api/cloudinary-sign — this is expected; Cloudinary's key is not confidential, only its API secret is.
  • Vehicle IDs are validated server-side before publishing, so a malformed ID can't break Website 1's /cars/<id> routing.
  • Cloudinary deletions and GitHub commits are restricted to this project's own folder/repo — the delete endpoint refuses to touch anything outside manchester-auto-cars/vehicles/.

Local Working Copy

This CMS keeps a working copy of the vehicle list in this browser's local storage so edits survive a page reload before you publish. It is not the source of truth — GitHub is. Resetting clears the working copy and reloads the bundled seed data; it does not affect anything already published.
